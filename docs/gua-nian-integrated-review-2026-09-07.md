## 1. [P1] 多页面重试确认会覆盖已经保存的编辑（复现 R3）

位置：`lib/chat-storage.ts:1296`、`lib/push-outbox-client.ts:220`，桥回复分支 `lib/push-outbox-client.ts:139` 也采用相同写回方式。

触发过程：两页都已缓存同一批回复，云端收取确认失败，回传箱仍保留该条目；其中一页把正文编辑并保存到 IndexedDB，另一页随后重试收取。`refreshChatSessionFromDisk` 只追加缓存中不存在的 ID，不更新已有 ID 的正文；命中批次后，`persistChatMessages` 又把旧缓存整批写回数据库。因此已经保存的编辑被旧正文覆盖。Web Locks 只串行化收取，不能解决缓存与编辑的版本关系。

验证：真实 Chromium、同源双 iframe、实际消费者与 Dexie 存储代码。两次确认失败后直接在共享数据库提交编辑，陈旧页面再确认；数据库正文从 `USER EDITED THIS REPLY` 回退为 `one reply`。传输和解析为桩，跨页锁与数据库真实运行。

修复方向：批次已经持久化时采用只读确认屏障，避免用缓存覆盖数据库。对确实未落盘的草稿另外处理；缓存刷新需要区分已提交记录和未提交草稿。验收必须包括编辑与删除后再重试确认。

## 2. [P1] 只镜像一个气泡就丢失该轮其余上下文（复现 R2）

位置：`lib/guanian-cloud-history.ts:46`、`:110`；两个云函数使用同一份注入逻辑。

触发过程：完整回复为“到了／我明天三点陪你去医院”。手机已完成收取确认，但聊天镜像暂时只上传了“到了”。组装历史时，只要发现任何一条相同 `response_batch_id`，就跳过整个已收取的 outbox 正文。结果历史只剩“到了”，约定内容消失。

这不是假设镜像违反事务：镜像队列按 50 条上传，和 outbox 收取确认是两条独立链路，没有整批镜像完成标记；50 条边界可以切开一轮气泡，后一请求也可能失败。读取最近 200 条的截断同样不能证明批次完整。

验证：运行实际共享历史函数，输入完整 outbox 和同批次首个气泡，输出历史只有首个气泡。当前防止“半轮消息”的分支仅覆盖尚未收取的 outbox。

修复方向：用批次完整性证据决定何时采用镜像版正文；未完整同步时保留完整事实来源，并正确处理用户编辑、删除后的版本，不能简单永远恢复原始正文。

## 3. [P2] 旧记录仅因时间接近就被排除，新约定无法触发核对（复现 R1）

位置：`lib/guanian-cloud-history.ts:94` 至 `:102`。

触发过程：旧云端消息 16:09 生成、18:52 收取；角色在 18:53 真正另说了“我明天三点陪你去医院”，但这条旧格式镜像没有批次编号。即使两段正文完全不同，当前兜底仍仅凭“收取延迟超过 3 分钟、镜像时间接近收取前后 2 分钟”，把新回复移入待核对附录并从 `messages` 移除。

附录保留原文不等于约定能被识别：约定门禁 `recheckEvidence` 只读取 `messages`。没有其他新用户消息或触发条件时，这个新承诺无法打开约定核对门禁；即使后来进入模型，附录还明确要求不能把它作为新承诺。

验证：实际历史函数与实际 `recheckEvidence` 串接，确认真实新回复被移出、`exactText=false`，且 `promiseUpdate=false`。原始数据库记录未删除，故障在判断链。

修复方向：时间邻近只能辅助寻找候选，不能单独判定一条发言不可作为新事实；保留无正文关联的独立发言，为确实含糊的匹配另建去重与核对策略。
