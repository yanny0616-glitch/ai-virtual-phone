# 冒险剧情时间

原有游戏从第 1 天清晨开始，对话、移动和裁决没有调用时段推进逻辑；休息只会进入次日清晨。现在时间随明确的剧情耗时推进，保留现有四时段：清晨、午后、黄昏、夜晚。

## 行为

- 短暂对话、即时反应和场景切换不强制耗时；处理一上午事务、等待到晚宴、赶路、过夜等由 DM 给出合适的目标时间。
- 每次场景/裁决请求携带当前存档的游戏日与时段，不能用旧对话时间覆盖。角色发言和调试预览也带相同的当前游戏时间。
- 合法变化保存到现有 `GameSave.gameDay/gameTime`，顶部自动更新；时间推进原因、本轮剧情日志和本轮自定义状态变更使用变化后的时间。休息操作仍明确进入次日清晨。
- 已有存档继续使用当前保存的时间，不猜测历史上应当流逝多久，也不要求重新创建世界。

## 协议与校验

DM 原有 JSON 增加 `time_update`：

```json
{
  "time_update": {
    "from": {"day": 3, "period": "morning"},
    "to": {"day": 3, "period": "afternoon"},
    "reason": "处理了一上午公事"
  }
}
```

无需变化输出 `null`；缺少字段兼容为不变化。day 必须为正整数，period 只能使用四个英文枚举值。返回绝对目标而非加几天；允许明确剧情导致多日跨度，不允许倒退、无效值或缺少原因的推进。计划、许诺、回忆不应推进当前时间，耗时是否合理仍由模型依据剧情判断。

`lib/adventure-time.ts` 的纯函数验证原值与本轮请求快照、当前存档时间，避免迟到结果覆盖休息或其他推进。API错误不会调用应用步骤；DM JSON经过旧修复器处理、或输出被截断时，时间更新会被标记无效并给出提示，不自动重发请求。

`lastTimeTurnId` 标记已处理的成功一轮（包含时间不变的情况）。`pendingEvent.timeTurnId` 保存当前行动编号，重新打开游戏后的失败重试继续沿用。显示层的 `skipDisplay` 不能当作重试判断：掷骰结果已显示而跳过重复显示的行动仍生成新编号，只有重试按钮明确复用旧编号。重复响应不再添加时间推进记录。游戏回档恢复快照中的时间和轮次记录。

## 验证范围

`node scripts/check-adventure-time.mjs` 验证纯规则、实际 DM 场景/裁决解析、自定义提示词仍追加时间协议，并通过 AST 提取和执行现有 MapView 的真实回调，检查初始场景、普通行动、自由交流后裁决、日志时间、重试与掷骰编号区别、API失败、休息，以及真实 persistSave 保存并恢复轮次编号。

`node scripts/check-adventure-status.mjs` 检查现有状态与世界编辑的提示词兼容，并检查角色实际发言和预览中的游戏时间。

所有模型回复为隔离测试数据，没有调用真实模型或执行手机端全流程。沿用原有时间显示，不新增开关或编辑界面；本机未运行全量构建。
