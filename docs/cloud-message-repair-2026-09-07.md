# 云端消息链路三项修复（2026-09-07）

状态：本地实现和专项验证完成；未提交、未推送、未部署。保留工作区原有约定 0.9.24 与其他修改。此记录针对用户确认的三项，不表示原审计全部关闭。

## 1. 消息误丢、旧轮完成后接续与生成结果恢复

对应原审计 A1、A2、A8、B14，以及相同 follow-up 次数误判。

回箱不再因为“预约后存在任意角色回复”、相同追问次数或相同 trigger_key 就直接确认消费。只使用明确的 outbox ID / responseBatchId 判断同一批；落盘失败不确认，确认失败可重试。

延后任务记录实际处理到的用户消息 ID，完成后保留精简回执。回箱落盘后立即结算对应轮次；轮询先发现完成也采用同一处理。如果用户在旧轮运行期间补充了尚未被纳入的消息，保存独立任务编号后建立下一轮。晚到的旧回执不能关闭新任务。云端已保存成文但仍待恢复投递时，对客户端返回运行中，禁止用补充消息覆盖旧成文。

模型返回后，先将回复、生成时间加密写回该任务，再进入投递步骤。成文后的租约失效、计划读取失败、回箱写入失败会重试投递已保存回复，不再从头调用模型。恢复前仍检查约定是否已撤销或改期。新任务不继承旧成文，模板也不保存临时追加的本轮历史。

## 2. 前台补收

对应 A3、A4。前台每 20 秒尝试补拉；启动、恢复网络、回到前台立即补拉，不依赖通知订阅是否存在。GET 和确认消费请求均有 15 秒超时；合并触发事件时保留立即补拉要求。

页面被系统挂起时轮询无法运行，恢复后补拉。消息仍显示云端生成时间，收取确认时间不代表阅读时间。这是页面收取改进，不保证系统通知准时展示。

## 3. 历史去重与时间统一

对应 A5、B11。有批次编号时按编号合并。旧数据没有编号时，仅在 consumed_at 前后 120 秒内，以完整正文或剥离内心后的完整正文匹配连续角色气泡；唯一匹配才合并，保留云端生成时间。模糊或多个候选保持原记录，避免误删真实发言；这是读取视图处理，不删除数据库记录。

生成器只追加一次云端事实历史。时间优先采用角色当天计划的时区，其次采用宿主传入的时区，再兜底 UTC。普通延后和推送预约上传宿主时区。

## 生效步骤与边界

宿主需要按现有 CI 发布；个人 Supabase 需要更新网关 ai-phone-push、push-generate、push-recheck。与此前约定改动一起交付时，仍需最新 schema 11 和挂念 0.9.24；本次三项本身没有新增 SQL 结构或 APP 版本。

若数据库连首次成文暂存都无法确认，不能保证恢复该结果；任务报告错误，不主动再次调用模型。微信或快捷动作已开始执行但结果未确认时，保留回复并标失败，需核对外部结果后恢复，不自动重放动作。

旧镜像无法唯一匹配时仍可能重复；已被旧逻辑确认丢弃的历史消息不会自动找回。多个标签页/PWA 同时消费的进程间竞争、设备接管、普通念头配额与 fresh 判据、旧 schema 持续重试等不在这次三项修复中，原审计中的这些问题不能标为已解决。
